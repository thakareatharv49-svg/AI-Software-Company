# M53 — Factory Job Queue & Mission Lifecycle

M53 makes missions first-class persistent jobs while preserving the M52 bounded factory scheduler.

## Lifecycle

A mission job uses these states:

- `queued`
- `running`
- `completed`
- `failed`
- `blocked`
- `cancelled`

Transitions are explicit and validated. Terminal completed/cancelled jobs cannot be restarted accidentally.

## Persistence

Mission metadata, generated plan, lifecycle status, message, attempt count, and timestamps are stored in `mission_jobs`.

On process restart, queued/running jobs can be recovered as queued jobs. Recovery is explicit; the system does not silently start model workloads.

## Factory integration

- Enqueuing a mission moves its job into `queued`.
- A factory attempt moves it to `running`.
- A bounded retry moves it back to `queued`.
- Successful completion moves it to `completed`.
- Exhausted failures become `blocked`.
- The control API exposes the lifecycle through mission records and a dedicated job endpoint.

## Safety

M53 does not add unbounded execution, time-based autonomous compute, or automatic restart execution. M52 retry limits remain in force.
